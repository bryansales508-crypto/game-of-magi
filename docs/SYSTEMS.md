# SYSTEMS

What every part of Game of Magi does today. The code under `src/` is the source of truth; this file describes it in plain language.

Paths are shortened: `Server` = `ServerScriptService/Server`, `Client` = `StarterPlayer/StarterPlayerScripts/Client`, `RS` = `ReplicatedStorage`, `RF` = `ReplicatedFirst`.

## How the code starts up

- **Server:** `Server/Main.server.luau` requires every ModuleScript in `Server/Services` (alphabetical), calls each `Init()` (must not yield), then calls each `Start()` on its own thread (may yield, may call other services). A failing service logs a warning and the rest keep running.
- **Client:** `Client/Main.client.luau` does the same for `Client/Controllers/*`.
- **Shared code** lives in `RS/Shared`: `Config.luau` (every tuning number, frozen), `Remotes.luau`, `SaveSchema.luau`, `Validate.luau`, `Log.luau`, `BehaviorTree.luau`, and `Data/*` (pure data: Alignment, Cities, Combat, DayNight, Economy, Epithets, Ranks, Regions, Shop).
- **Studio-only art** (maps, GUIs, sounds, models) is not generated by code. The code looks it up by name at runtime, for example `Workspace.MAP.Spawns.QarzinSpawn`, `Workspace.MAP.MISSION.<City>Delivery`, `Workspace.Regions`, `Workspace.Qarzin.ClothesStand`, `RF.SFX`, `RF.VFX`, `RF.GUI`, `RF.AfterLife`.

## 1. Join and saves

**What it does.** Every player gets one save, loaded when they join and written when they leave. A separate pipeline walks each spawn through "loading", "loaded" and "ready" so no system acts on a half-built character.

**Files:** `Server/Services/DataService.luau`, `Server/Packages/ProfileStore.luau` (vendored library, unchanged), `Server/Services/PlayerService.luau`, `RS/Shared/SaveSchema.luau`; client `Controllers/LoadController`.

**Saves (DataService).**
- ProfileStore session-locks each save, so two servers can never hold the same one. It saves on leave and on server shutdown.
- Store name `Config.Data.StoreName` (`GameOfMagi_v1`). Key: `<SaveScope>_<userId>`, where `SaveScope` is `Studio` in Studio and `Live` on a published server, so Studio tests never touch live saves.
- `Config.Debug.FreshSave` (Studio only) puts every session on ProfileStore's in-memory mock: nothing persists. DataService also falls back to the mock for the rest of that server's life if the first real session call throws in Studio. On a live server a load failure kicks the player ("Your save couldn't be loaded. Please rejoin in a moment."); a stolen session or a DataStore outage mid-session does the same.
- API: `Get`, `WaitFor(player, timeout?)`, `IsLoaded`, `Loaded` (signal), `Replaced` (signal, fires when a save is replaced in place so attribute mirrors can re-publish), `OnReleasing(handler)` (runs before the profile is released, so handlers can still read it), `Save`, `Wipe` (full reset, clears the combat unlock), `NewLife` (reset for a new character; keeps `Meta.Lives` plus one, `Meta.Created` and `Meta.Unlocks.Combat`), `ResetToTemplate` (the shared reset step).

**Save shape (schema version 5, `SaveSchema.Template`).**
```
Version   5
Character = { FirstName, Gender (0 = not chosen), Race (2 = Human), Kingdom, SkinTone (0 = not chosen),
              HairColor {R,G,B}, EyeColor, FaceBase, MouthShape,
              Height (10 = not rolled yet), GrowthProfile ("v1|start|adult|spurtAge|fatEnd"),
              LivesLeft }
Age       = { Years (starts 13), TimePassed (os.time of last aging tick), ProgToAge (seconds banked) }
Progress  = { Magoi, GoldRukh, BlackRukh, Epithet,
              PendingEpithet? = { rank, choices {3 strings} },
              DeliveryStreak, Routes = { [cityKey] = count }, Intercepted,
              Wanted? = UserId of the bounty a hunter holds (nil = none), JailUntil (os.time, 0 = free) }
Bounty    number
Economy   = { Copper (starts 20), Silver, Gold }
Gear      = { Shirt, Pants, Hats {3 slots}, Inventory {item codes} }
Family, Magic   reserved, empty
Meta      = { Created, LastSeen, Lives (how many characters this player has had),
              Unlocks = { Combat } }
```
- Missing keys are filled from the template by `Profile:Reconcile()`, then `SaveSchema.Migrate` walks an old save up one version at a time. v2 and v4 are empty migrations (new optional fields); v3 grants existing saves the combat unlock and a full set of lives; v5 sets `Progress.Wanted` nil and `Progress.JailUntil` 0 (M9 bounty hunting and the jail). A brand-new save is created already at the current version, so no migration runs on it.
- `SaveSchema.NewLife` rolls the random first-time look (first name, hair colour, eye colour, face base, mouth shape).
- **Changing the save format means updating this section** and adding a migration.

**Join pipeline (PlayerService).** One Player attribute, `JoinState`, is `"Loading"`, `"Loaded"` or `"Ready"`, reset to `"Loading"` on every spawn and respawn.
1. On each spawn it waits for `HumanoidRootPart` (10 s, then logs an error rather than hanging) and moves the character to `Workspace.MAP.Spawns.QarzinSpawn`. Every spawn goes to Qarzin; no position is saved.
2. Once the save is loaded, `JoinState = "Loaded"`.
3. The client's loading screen fires `ClientReady` when it finishes. The server accepts it only while the state is `"Loaded"`, then sets `"Ready"` and fires `PlayerService.Ready(player, character)`. Later systems wait on that signal.
4. A character stuck in "Loading" for 120 s logs one warning and keeps waiting; it never kicks.
- API: `GetState`, `IsReady`, `WaitForReady(player, timeout?)`, `Ready`, and the pure `NextJoinState(state, event)`.
- **Remote:** `ClientReady` (client → server, no args, 3 per 10 s).
- **Attribute:** `JoinState` (Player).

**Client (LoadController).** Shows the loading screen on every spawn, waits for `JoinState == "Loaded"`, fades out, then fires `ClientReady`.

## 2. Character creation and appearance

**What it does.** Builds each character's look from the save. A brand-new life first shows the gender and skin picker; once the player picks, the character is built.

**Files:** `Server/Services/CharacterService/init.luau`, `CharacterService/FaceControl/init.luau`, `RF/Assets/init.luau` (data: face decals, names, outfits, hats, cloaks, item lookup); client `Controllers/CreationController`.

- CharacterService runs on `PlayerService.Ready`. It publishes the Player attributes first, even before a gender exists, so the client knows to open the creation screen.
- **Creation screen (CreationController).** Clones `RF.GUI.Gender`, removes its embedded server script, and lets the player pick gender (1 or 2) and skin (1–3). Enter fires `CreateCharacter`. The screen closes when the `Gender` attribute becomes non-zero.
- **`CreateCharacter`** (client → server, `gender 1|2`, `skin 1|2|3`, 3 per 10 s). Ignored unless the save's `Character.Gender == 0`. It stores gender and skin and rolls a first name from the matching gender's list. A repeat call after gender is set logs a throttled warning.
- Once a gender exists, a new life rolls its growth profile (`AgeHandler.start`, which needs the gender), then the build runs: strips the default Roblox avatar, picks the skin template **by name** (1 Black, 2 Brown, 3 White; Kingdom 1 swaps White for LightTan, Kingdom 2 swaps Black for Tan and Brown for LightTan), adds a `FalseHead` with face decals (each decal in its own `pcall`, so one bad read drops only that decal), tints hair to the saved colour (greyed by age, see section 3), adds the combat hitbox, the shared collision group, sounds and particles (found once at boot by name, searching `RF.SFX`/`RF.VFX` recursively; a missing one warns once), the saved shirt, pants and hats (or a random starter rag outfit for a new life), and the custom run/walk/jump/idle/fall animations (`Config.Character.Animations`). Last, it sets `character.AppearenceLoaded = true` (original spelling), which several systems wait on.
- `FaceControl` runs once per character: mouth flaps while chatting, random blinking, hurt and knocked-out faces from the `Hit` and `Ragdoll` effect markers. Its connections are cleaned up when the character is destroyed.
- `HideOverheadDisplay` hides Roblox's default name and health bar on player characters. NPC trainers keep their own billboards.
- **Player attributes:** `Gender`, `SkinTone`, `Kingdom`, `FirstName`, `HeightStuds` (display only), `Lives` (character count), `Age`.
- **Depends on:** DataService, PlayerService, ItemService, AgeService (`AgeHandler`, `ApplyHairColor`), `RF.Assets`, `RF.SFX`, `RF.VFX`.

## 3. Aging, death and lives

**What it does.** Characters age in real time, grow and grey as they do, and eventually die of old age. Separately, each character has a few lives that real deaths use up.

**Files:** `Server/Services/AgeService/init.luau` (plus `AgeHandler.luau` growth maths and `HeightHandler.luau` body resizing), `Server/Services/LifeService.luau`; client `Controllers/RukhController`.

**Aging (AgeService).**
- One shared loop (`Config.Aging.Tick`, 10 s) banks real seconds, times `DevService.GetTimeScale()`, into `Age.ProgToAge`. Every `Config.Aging.SecondsPerYear` (60 s in Studio, 1800 s live) is a birthday: `Age.Years += 1`, the body is resized to the growth profile, worn hats and cloaks are re-fitted, hair colour is re-applied, and the `Age` attribute updates. The body is also resized on every spawn.
- **Offline aging:** once per session, on load, the player ages up to `Config.Aging.OfflineYearsPerDay` (2) per real day away, capped at `OfflineAgeCap` (59). It is never fatal. Leftover fractions of a day are dropped.
- **Visible aging:** the applied hair colour lerps toward grey from `GreyStart` (45) to `GreyEnd` (70). The saved colour never changes. There is no wrinkle art yet.
- **Growth profile:** `"v1|startHeight|adultHeight|spurtAge|fatEnd"`, rolled once per life (female growth factor 0.9). `HeightHandler` resizes body parts, joints, attachments and accessories; hair follows the head's smaller ratio.

**Old-age death.**
- From `Config.Aging.DeathStart` (60), every online birthday fires `HeartAttack(age, fatal)`. `fatal` is rolled from `Config.Aging.DeathChance` (interpolated between its age/chance points) but only when `DevService.IsMortal()` is true: off by default in Studio, always on live. With mortality off the roll is skipped, but the non-fatal pulse still plays.
- `AgeService.StartDeathSequence(player, data, cause)` is the shared death path (`cause` is `"heartAttack"` or `"lastLife"`). It sets the Player attribute `Dying`, freezes the humanoid, runs `DataService.NewLife` immediately (so leaving mid-scene still gives a fresh life), waits for the client's `RukhSceneDone` or `Config.Aging.SceneTimeout` (30 s, not time-scaled), then calls `LoadCharacter`. `ForceBirthday`/`ForceHeartAttack` refuse while `Dying` and return `(ok, reason?)`.

**Lives (LifeService).**
- Each character starts with `Config.Life.LivesPerCharacter` (4) lives in `Character.LivesLeft`, mirrored to the Player attribute `LivesLeft`.
- A real `Humanoid.Died` (fall, void, drowning) costs one life. A combat knockout never fires `Died`, so it never costs a life. `LifeService.HandleDeath(data)` is the pure decision: `"respawn"` or `"lastLife"`.
- With lives left, the same character respawns after `Config.Life.RespawnDelay` (3 s), guarded so it does nothing if something else already respawned the player. The last life fires `Died({cause = "lastLife"})` and runs the same afterlife scene as a fatal heart attack, ending in a brand-new character.
- At `Init`, LifeService sets `Players.RespawnTime` to `Config.Life.EngineRespawnSeconds` (3600), so the engine never respawns anyone on its own; every death is respawned by LifeService, AgeService or the join pipeline.
- The combat unlock (`Meta.Unlocks.Combat`) survives new characters; only `.fresh` clears it.

**Client (RukhController).** Plays the heartbeat pulse for each `HeartAttack`, and on a fatal one (or on `Died`) the return-to-the-Rukh scene: input frozen, camera scripted, the character turns golden, walks toward a core, fades to white, then fires `RukhSceneDone`. Every timing is in `Config.Scene`; the heartbeat sound is `Config.Sfx.Heartbeat`. The art is Bryan's `RF.AfterLife` model; the controller reads only `AfterlifeCamera` (camera spot), `AfterlifeSpawnBlock` (where the character stands) and the optional `AfterlifeCore` (what it walks toward). Missing pieces fall back to a plain stand-in.

**Remotes.** `HeartAttack(age, fatal)` and `Died({cause})` (server → client only); `RukhSceneDone()` (client → server, 2 per 60 s).
**Attributes.** `Age`, `Lives`, `LivesLeft`, `Dying` (Player).
**Dev commands.** `.birthday`, `.heart [fatal]`, `.lives <n>`, `.kill`, `.age`, `.age+`, `.mortal on|off`, `.timescale <n>`.

## 4. Health and status

**What it does.** `HealthService` owns health and block; `StatusService` owns timed combat conditions such as stun and knockout. Players and NPCs go through the same code, keyed by their character model.

**Files:** `Server/Services/HealthService.luau`, `Server/Services/StatusService.luau`.

**HealthService.**
- `Humanoid.Health/MaxHealth` is the one source of truth. Max health is `MaxHealthFor(height, rankIndex)`, so being taller and ranking up both raise it. A rank-up keeps current health unless the character was full.
- Block, max block and the regen tier (`Idle`, `Combat`, `Knocked`) are per-spawn runtime state, not saved. One loop regenerates health and block at a flat per-second rate for the current tier and ticks Bleed damage.
- API: `TakeDamage`, `SetTier`, `SpendBlock`, `SetBlocking`, `IsBlocking`, `Register(character)`/`Unregister` (NPCs; max health from `Config.Npc.MaxHealth`), `MaxHealthFor`, `RegenAmount`.
- **Attributes** (on the Player, or the NPC model): `Health`, `MaxHealth`, `Block`, `MaxBlock`, `RegenTier`. The HUD reads these.
- **Dev commands:** `.hp <n>`, `.tier <Idle|Combat|Knocked>`.

**StatusService.**
- Statuses: `Hit`, `Stun`, `Knocked`, `Ragdoll`, `Block`, `BlockBroken`, `TrueStun`, `LightStun` (can't block or parry, can still attack or dash), `Recovery` (a punished feint: can't attack, block or dash) and `Bleed` (stacked; ticked by HealthService).
- API: `Register(character, owner?)`, `Unregister`, `Apply(character, status, duration?, data?)`, `Remove`, `Has`, `Get`, `IsRegistered`, plus a Changed signal. Statuses with a duration expire on one shared loop; re-applying refreshes the timer.
- Players register automatically on `PlayerService.Ready`; NpcService registers NPCs.
- Some statuses publish a boolean character attribute for clients; `Bleed` publishes its stack count.
- **The Effects bridge.** Every status also creates or removes a marker Value under `character.Effects`. Client scripts react to those markers: the face control, sounds and particles, the ragdoll, the knockout screen, the mission fragile-hit check. If something destroys a marker, StatusService treats the status as ended. For players the `Effects` folder is created by `RagdollService` once `AppearenceLoaded` is true; NPCs get one from StatusService after a bounded wait.

## 5. Movement

**What it does.** `MovementService` is the only thing that sets `WalkSpeed`. Walking, running, dashing and every slowdown go through it.

**Files:** `Server/Services/MovementService.luau`, `RS/Modules/SpeedHandler.luau` (small helper), client `Controllers/CombatController` (sends the inputs).

- **Speed stack.** Each combatant has a set of named multipliers. The effective multiplier is the *smallest* active one (0 freezes). The baseline is walk 16 or run `16 × Config.Combat.Run.speedMult`; the stack applies after that choice. `LowHealthMult(running, ratio)` slows a hurt character (down to 0.5× running, 0.25× walking at zero health) without ever speeding it up.
- **Run:** `Run(boolean)` is an intention. The server ignores it while stunned, knocked or blocking.
- **Dash:** `Dash(x, z)` takes a direction in the character's local space, clamped to [-1, 1] and normalised so a diagonal isn't faster. Server cooldown (`NextDashAt` attribute); refused while stunned or knocked. The dash distance shrinks with low health and scales by every active movement modifier.
- **Modifiers:** `SetModifier(character, name, mult)` / `ClearModifier`. Missions use `HeavyCargo` (0.75×). `SetStyle(character, styleName)` applies a fighting style's `speedMult` and `dashCooldownMult`.
- Bridge for older readers: `character.IntFold.MovementSpeed` has one child per modifier and `IntFold["Running?"]` mirrors the run flag.
- **Remotes:** `Run(boolean)` (4 per 1 s), `Dash(x, z)` (2 per 1 s), both client → server.
- **Attributes (character):** `SpeedMult`, `Running`, `NextDashAt`.
- Client side: `Animate` (stock-style animation script in `StarterCharacterScripts`) plays the locomotion animations; run-step sounds come from FootstepController (section 14).

## 6. Combat (shelved)

Combat is shelved for a from-scratch redesign after the other systems are finished. This is what runs today, kept minimal on purpose.

`CombatService` (server-authoritative, keyed by character model so NPCs use the same entry points) runs a click-driven combo for the equipped fighting style (`Fist` or `Dagger`, defined in `Shared/Data/Combat.luau` as a chain of hits plus traits). The client (`CombatController` with `SwingTrack`) sends intentions only: `AttackStart`, `AttackHit` (which hit marker just played), `AttackContinue` (the next click), `AttackCancel`, `Block`, `SetStance`. The server checks timing windows and the attacker's position and works out the target itself. Every hit applies `LightStun`; hits and blocks go through `StatusService` and `HealthService`. The server broadcasts `CombatEvent(name, data)` (Swing, SwingContinue, Hit, Miss, Blocked, Parried, BlockBroken, Knocked, KnockedBack, Bleed, AttackCancelled, AttackEnded, Recovered) and `EffectsController` plays the sounds and particles. Attacks are refused unless the character's `InCombat` attribute is true. Combat access is the Player attribute `CombatUnlocked` (`Meta.Unlocks.Combat` or `Config.Combat.UnlockedByDefault`). `CombatService.HitLanded` is the signal that missions listen to. Dev commands: `.combat log on|off`, `.knock`, `.stun`, `.weapon`, `.style`, `.unlock combat`, `.lock combat`. The animation-driven swing track is shared by `NpcAnimController` so dummies swing like players.

**Remotes:** `AttackStart`, `AttackHit(index)`, `AttackContinue(index)`, `AttackCancel`, `Block(boolean)`, `SetStance(boolean)` (client → server, rate-limited); `CombatEvent` (server → client). **Attributes:** `InCombat`, `Attacking`, `ComboStep`, `CurrentHitIndex`, `NextAttackAt`, `HitCount`, `WeaponSet`.

## 7. NPCs and trainers

**What it does.** Dummies in `Workspace.NPC` and spawned trainers are real combatants driven by behaviour trees. The models stay in Workspace as art; the service finds and drives them.

**Files:** `Server/Services/NpcService/init.luau`, `NpcService/Trees.luau`, `NpcService/AiController.luau`, `RS/Shared/BehaviorTree.luau`; client `Controllers/NpcAnimController`.

- Each NPC registers with StatusService, MovementService, HealthService and CombatService exactly as a player does. One shared loop ticks every NPC's tree every `Config.Npc.TickSeconds` (0.2 s), not one thread each.
- `AiController.new(character, npcType, tree)` holds a per-NPC blackboard that the tree reads and writes. `BehaviorTree` supplies the nodes (selector, sequence, cooldown, wait, condition, action).
- `Trees.BuildDummy()` and `BuildTarget()` build fresh trees per NPC. `Trees.BuildTrainer(key)` builds a trainer from `Config.Npc.Trainers[key]`. `WeightedPick` rolls weighted moves.
- **Trainers** (`Config.Npc.TrainerOrder`): StraightSam, TurtleTariq, JabbingJamal, ParryPete, FeintingMohammed, DashingDalila, SparringSinbad. Each practises one combat skill. They are spawned into their own `Workspace.Trainers` folder so the dummy watcher doesn't register them twice, with a name tag above them.
- **Target grips (M9-04).** The Target tree has a branch before its attack: when its target is `Knocked` (and not carried, jailed or gripped by someone else) and `Config.Npc.Target.gripsOnKnockout` is true, it walks to within `Config.Npc.AttackRange` and calls `GripService.Begin(npcModel, targetPlayer)` (Running while the grip holds). A landed hit on it or a knockout of it breaks the grip like any other; it may start again once the victim's grace Knocked is the only thing keeping them down. Trainers never grip.
- `NpcType` attribute is `Dummy`, `Target`, or a trainer; `ResolveNpcType` reads it from the model.
- **NpcAnimController (client).** NPCs have no client of their own, so every client animates them from server state: locomotion off `Humanoid.Running`, the combat stance and dagger prop through CombatController, and the combo through `SwingTrack` driven by `CombatEvent`/`SwingContinue`.
- **Dev commands:** `.npc list|reset|type <name> Dummy|Target`, `.dummy spawn <name> [player] | clear | list`.

## 8. Ragdoll

**What it does.** When `Knocked` turns on for any combatant, its joints are built into a ragdoll; when it ends, they are removed.

**Files:** `Server/Services/RagdollService.luau`, `RS/Modules/Ragdoll/` (`init.luau`, `LimbTree.luau` and the per-joint `.rbxm` templates).

- Players: the owning client's `EffectsController` flips the Humanoid between Physics and GettingUp; the server leaves a player's Humanoid state alone. NPCs have no such client, so the server sets their state.
- Also creates `character.Effects` for players (see section 4) and writes the `Ragdoll` marker beside `Knocked`.
- API: `RagdollService.IsRagdolled(character)`.

## 9. Rank, alignment, Rukh and epithets

**What it does.** Magoi (experience) decides rank. Deeds build two hidden tallies, Gold Rukh and Black Rukh, which decide alignment. Each rank-up offers a choice of epithet.

**Files:** `Server/Services/RankService.luau`, `RS/Shared/Data/Ranks.luau`, `Alignment.luau`, `Epithets.luau`; client `Controllers/RankController`.

- **Ranks** (Magoi thresholds): Street Rat 0, Wanderer 300, Adventurer 600, Renowned 1500, Hero 2400, Legend 4200, King/Queen 6000. `Ranks.titleFor(magoi, gender)` picks King or Queen.
- **Alignment** is a mix of the two tallies, classified by `Alignment.alignmentFor` as White (not enough deeds yet), Gold or Black.
- **Epithets.** At birth and at each rank-up the server rolls three choices from the bank for that rank and alignment, stores them in `Progress.PendingEpithet`, and waits for the player's answer. A pending choice is never overwritten, and a single big gain walks the player forward one rank at a time.
- Every change goes through `RankService.AddMagoi(player, amount, reason)` and `AddDeed(player, kind, amount)`, which check rank and alignment where the number changes; there is no polling loop. Mission payouts and the dev commands use these.
- API: `GetRank(player)` → `(rankIndex, title)`, `GetAlignment`, `TitleForIndex`, plus pure helpers used by the self-tests.
- **Remotes:** `RankUp({title, rankIndex, alignment, choices, origin})` and `AlignmentChanged({alignment})` (server → client); `ChooseEpithet(index 1–3)` (client → server, 3 per 10 s; the server trusts only the index into the three it stored).
- **Attributes (Player):** `Rank`, `RankIndex`, `Epithet`, `Alignment`, `EpithetPending`.
- **Client (RankController).** Shows the rank-up moment, the Rukh "flutter" on a gain, and the epithet card, which reuses the menu card's look and fonts. The card closes when `EpithetPending` goes false.
- **Dev commands:** `.magoi`, `.magoi+`, `.rukh <gold> <black>`, `.rankup`, `.epithet clear|<text>`, `.bounty`.

## 10. HUD and menu

**What it does.** Shows health and block bars, the character menu card, the backpack, and chat-style prompts.

**Files:** client `Controllers/HudController`, `Controllers/MenuController`, `Controllers/HotbarController`; art in `StarterGui/HUD` and `RF/GUI`.

- **HudController.** Drives the health and block bars from the `Health`, `MaxHealth`, `Block`, `MaxBlock` attributes. The HUD ScreenGui resets on every respawn, so the controller re-finds the bars and reconnects each time.
- **MenuController.** The M-key card. Clones `RF.GUI.UIGUI.MenuGUI` once, destroys its embedded `MenuMechanics` script, and fills it from attributes (`FirstName`, `Kingdom`, `Age`, `HeightStuds`, `Rank`, `Epithet`, `Alignment`, `Lives`). Values show "..." until they arrive.
- **HotbarController.** The hotbar (10 slots, keys 1-9 and 0) and the inventory panel (backquote or the arrow opens it; drag slots between the two, double-click to send a tool back to the hotbar, search box), built from the `RF.GUI` `SlotFrame`, `ToolIcon`, `ToolName` and `Number` frames. It only shows the Backpack and equips through `Humanoid:EquipTool`/`UnequipTools`; the only tools in play are the weapon tools. Its ScreenGui survives respawns and the slots are refilled from each new character's tools.
- **Input freezing.** Nothing writes `FreezeInput`, `BigFreezeInput` or `ActionFreezeInput` into `character.Effects` any more, so the old input sinks are gone; the knockout freeze is EffectsController's. Server-to-client chat lines are `CoinMessage` (section 11); the old `ForcedChat` remote has no sender or listener.
- **EffectsController** (combat feedback) is covered in section 6.

## 11. Currency

**What it does.** `EconomyService` owns the wallet. Prices are exact-coin: a Silver price can only be paid in Silver, never made up from Copper and Gold.

**Files:** `Server/Services/EconomyService.luau`, `RS/Shared/Data/Economy.luau`; client `Controllers/CurrencyController`.

- **Coin values.** 1 Gold = 100 Silver = 10,000 Copper. A price or reward shows in exactly one coin by bands: 1–100 Copper shows as Copper; every further 100 Copper adds one Silver (101–200 is 1 Silver); past 10,000 Copper the same banding carries into Gold. `Economy.toPrice(copper)` and `Economy.format(coin, amount)` do this.
- API: `Get`, `CanAfford(player, coin, amount)`, `Pay(player, coin, amount, reason)`, `Give`, `GiveCopperValue(player, copper, reason)` (rewards pay Copper only). Nothing converts coins; that is a future Bank's job.
- A failed `Pay` fires `CoinMessage` with a flavour line: "I need more money..." when total wealth falls short, or a "this place only takes Silver" style line when it doesn't convert.
- **Attributes (Player):** `Copper`, `Silver`, `Gold`, kept current on every change (including when a save is replaced).
- **Remote:** `CoinMessage(text)` (server → client).
- **Client (CurrencyController).** Drives the purse HUD (`StarterGui.Currency`, found in PlayerGui and rebound on each respawn), plays one restartable coin sound on every purse change, and posts `CoinMessage` text to chat as the character speaking.
- **Dev commands:** `.coins`, `.coins+`, `.price <copper>`, `.pay <coin> <amount>`.

## 12. Clothes shop

**What it does.** The stand in Qarzin sells shirts, pants, hats and cloaks. Buying wears the item and saves it.

**Files:** `Server/Services/ShopService.luau`, `Server/Services/ItemService.luau`, `RS/Shared/Data/Shop.luau`; client `Controllers/ShopController`.

- **Item codes.** Every wearable is a string `"type|name|r,g,b"` (`S` shirt, `P` pants, `H` hat, `C` cloak; colour 0–255).
- **ItemService.** `Equip(code, character)` puts an item on, recolours it and resizes it to the current body. `Owns(data, code)` is colour-aware (the same item in a different colour is a different item). `HasFreeHatSlot` (hats and cloaks share the 3 slots). `Wear(player, code)` equips and writes `Gear.Shirt`, `Gear.Pants` or the first empty hat slot.
- **Shop.luau** is pure data: colour pools and weights, hat and cloak name lists, shirt and pants pools (the starter rags are not for sale), display offsets, and `PriceFor(itemType, color)`, shown through the currency bands.
- **ShopService** stocks `Workspace.Qarzin.ClothesStand` once, `Shop.StockDelaySeconds` (5 s) after server start: random hats on the hat table, shirts and pants on the racks, a cloak on every cloak stand. Each item has a ProximityPrompt with the price as its text. On trigger the server runs every check before charging: free slot, not already owned (`Decide` returns `"ok" | "slotsFull" | "owned"`), then `EconomyService.Pay`; only then `ItemService.Wear`. Failure lines go through `CoinMessage`. Empty racks have no prompt or highlight.
- **ShopController (client).** The hover highlight is local only: a ClickDetector or the prompt on the rack's highlight part sets the rack's `Highlight` and part transparency for that player alone, one rack at a time, with a reach fallback for gamepad and touch.
- **Dev commands:** `.shop restock`, `.shop list`.

## 13. Delivery missions

**What it does.** A courier opens a board at a city's delivery post, picks a destination, carries a package there for Copper, Magoi and Gold Rukh, and can be intercepted along the way.

**Files:** `Server/Services/MissionService.luau`, `RS/Shared/Data/Cities.luau`; client `Controllers/MissionController`; art in `RF/GUI/MissionGUI` and `RF.Objects` (packages).

- **Cities** (`Cities.luau`): Qarzin, Sahraqin, Illegal Port, Ain Jamala, Saleh, Rathole, Jaddaty's Hut. Each has lore text, a board colour, a population, a static Safety rating (0–1) and a trade-route list. Only Qarzin is built; the rest are markers.
- **Board.** The client fires `MissionOpenBoard(cityKey)` within `Config.Missions.OpenStuds` (12) of `Workspace.MAP.MISSION.<City>Delivery`; the server checks the distance. It rolls 0–3 modifiers per route destination and sends `MissionBoard`. Rolls are cached per player per destination until a run starts, so reopening can't fish for a better roll. `MissionStart(destinationKey)` is accepted only for a destination on the open board. A missing delivery part is replaced by a placeholder drop-off (`PlaceholderPosition`, swept by `SweepPlaceholders`); `DestinationPositionFor` is also used by `.tp`.
- **Modifiers** (one shared table; each has `key`, display `name`, roll weight shown as `chance`, text): TimeCrunch, CourierLoop, HighlyValuable, HeavyCargo, VIP, FragilePackage, CleartheRoute. They roll from the player's own `Progress.Routes[destination]` count and the destination's Safety.
- **A modifier failing never ends the run.** It marks only that modifier failed (`MarkFailed`, idempotent) and drops its multiplier from the payout, and the client greys its pop-out through a `ModifierFailed` update. TimeCrunch fails after `TimeCrunchSeconds` (180 s); FragilePackage and VIP fail on any landed hit (via `CombatService.HitLanded`); CleartheRoute fails unless the courier is credited with a knockout during the run. HeavyCargo slows the courier (0.75×) and scales the package up. CourierLoop sends the courier back to the start after the first arrival (a `"Started"` update with `returnPosition` and the `failed` list). HighlyValuable gives only a pay multiplier plus a permanent gold glow on the package. Only leaving, dying, respawning, an interception or `.mission fail` end a run early.
- **Payout.** `floor(1 + 10/rankIndex + population×1.25 + streak×1.25)`, times the combined multiplier of the intact modifiers (additive: `1 + Σ(multiplier − 1)`), times the intercepted-mark offer multiplier. Paid as Copper through `EconomyService.GiveCopperValue`, plus `MagoiPerDelivery` (10) Magoi and 1 Gold Rukh through RankService. A completed delivery adds 1 to `Progress.DeliveryStreak` and to `Progress.Routes[destination]`; any failure or interception resets the streak. Arrival is within `ArriveStuds` (10), checked on one shared 0.5 s loop together with the timer and beacon.
- **Interception.** If the courier is knocked out by another player (resolved by UserId), and the courier is at least `InterceptMinStuds` (100) from the start or `InterceptMinSeconds` (30) into the run, the run settles as `"Intercepted"` exactly once (`TrySettle`): the courier's save is untouched, and the attacker is paid instantly (`InterceptPay`, which excludes CleartheRoute and ignores the fatal hit's own modifier failures) plus usually 1 Black Rukh, and `Bounty` rises (through `BountyService.Add`, section 17). A knockout outside those limits, or with no player attacker, just fails the run.
- **Intercepted mark.** Each interception adds a stack to the courier's `Progress.Intercepted`. `OfferMultiplier(stacks) = max(InterceptedFloor, InterceptedDecay ^ stacks)` (1× at none, 0.5× at one, floor 0.1×). It scales every board offer, that courier's own next payout, and an interceptor's payout. It is read fresh each time (never baked into the cached roll) and cleared only after a completed delivery pays. A second interception of an already-marked courier gives no Black Rukh (`InterceptorEarnsBlackRukh`).
- **Package.** A package is strapped to the courier's back; `CourierBeacon` (character attribute) makes the courier visible: a 30 s on / 3 s off cycle, permanently on for HighlyValuable.
- **Remotes:** `MissionOpenBoard(cityKey)`, `MissionStart(destinationKey)`, `MissionExit()` (client → server, 2 per 1 s; city keys are validated against `Cities.Keys`). `MissionBoard({city, destinations{key, name, color, lore, image, pay, modifiers{key, name, chance, text}}, intercepted, offerMultiplier})` or nil to close; `MissionUpdate({state = "Started"|"Finished"|"Failed"|"Intercepted"|"Cleared"|"ModifierFailed", modifiers, failed, timerEnds, returnPosition, key})` (server → client).
- **Attributes:** `OnMission`, `MissionDestination`, `MissionStreak` (Player; `Bounty` now belongs to BountyService); `CourierBeacon` (character).
- **MissionController (client).** Draws the board (city buttons in the old Frame/TextButton layout, per-city colours, modifier cards showing the chance percentage, the pop-outs), the quest tracker (kept clear of FOV changes), and the courier beacon (fades over 45 s).
- **Dev commands:** `.mission start <city> | finish | fail | streak <n> | mark [n] | intercept | log on|off`, plus `.tp <city>`, which falls back to a city's drop-off or region when it has no spawn.

## 14. World

**What it does.** Everything that makes the world feel alive: where you are, what music plays, the time of day, footsteps, and who collides with whom. All of it runs on the client except the clock and collision groups.

**Regions and music.**
- `Client/Controllers/RegionController`: every BasePart named `<Key>REGION` under `Workspace.Regions` is a box. Every `Config.World.Music.RegionPollSeconds` it tests the player's position against the boxes with plain maths (no Touched), and fires Entered/Left locally. API: `Current()`.
- `Client/Controllers/MusicController`: plays the highest-priority region's playlist, shuffled without repeating the last track, crossfading between tracks and regions; each region's `ambient` loop is its own layer. A city banner (the `MsgHold[CITY]` template) bounces in on entry. Tracks come from `RF.SFX.OSTs`. A bottom-left music panel shows the track and volume. API: `Current`, `Play`, `Stop`, `SetVolume`/`Volume`, `PlayForced`.
- Data: `Shared/Data/Regions.luau` (Qarzin, SakuraIsland, Ocean: playlist, ambient, banner). Local commands: `.region`, `.music [stop|play|next|volume <0-1>|<track>]`.

**Day and night.**
- `Server/Services/WorldClockService`: the server never touches Lighting. It publishes Workspace attributes `DayStart`, `DayLength` and (only while paused) `DayPaused`; one in-game day is the day part plus the night part from `Config.World.DayNight`. API: `ClockTimeAt`, `CurrentHour`, `SetHour`, `SetSpeed`, `Pause`, `Resume`, `IsPaused`, `GetSpeed`. Dev command: `.time [0-24 | speed <x> | pause | resume]`.
- `Client/Controllers/LightingController`: every frame derives the hour from those attributes and blends Lighting between the Day, Dusk, Night and Dawn palettes in `Shared/Data/DayNight.luau`. It also switches the `CityLight` tagged lights on at night. Local command: `.lights on|off|auto`.

**Footsteps.**
- `Client/Controllers/FootstepController`: listens for the `FootstepEvent` that `Animate` fires on each step marker. Plays a sound chosen by floor material (clips from `RF.SFX.Steps`), louder when the `Running` attribute is set, silent while `character.Effects.MutedStep` exists, and leaves a fading print on Sand or Mud. A fallback step timer covers a missing marker; `Config.World.Footsteps.Debug` logs it.
- `StarterPlayerScripts/RbxCharacterSounds.client.luau` replaces Roblox's default sound script: it plays every default sound except the Running footstep, so FootstepController's steps are the only ones. `RS/Modules/ColorMath.luau` is a small colour helper used by the footprints.

**Ocean (switched off).** `Client/Controllers/OceanController` moves the `MovingPart`/`OceanWaves` tiles under `Workspace.MAP.OCEAN` and fades their wave decals from one place, near the camera only. `Config.World.Ocean.Enabled` is `false`; the old per-part wave scripts it was waiting on are now deleted, so it can be switched on.

**Collisions (`Server/Services/CollisionService`).** Every BasePart under `Workspace.MAP` joins `MapCollisionGroup` (except under a folder named `Areas`); parts inside a model named `ClothingRack` join `ClothingRackGroup` so players walk through racks. `CharacterService` registers the `PlayerLimbs` group once. API: `AssignMapPart`, `AssignTree`.

## 17. Bounty Hunting (M9-01)

Server: `Server/Services/BountyService.luau`. Data: `Shared/Data/Bounty.luau` (pure rules), `Config.Bounty` (the numbers). Intercepting a courier is the only crime in this pass; knocking someone out adds nothing (it could be farmed).

- **Bounty.** `BountyService` owns `Bounty` on the save and the `Bounty` Player attribute (re-published on load and on `DataService.Replaced`). `Add(player, amount, reason)`, `Get`, `Set` (dev), `IsWanted` (bounty >= `Config.Bounty.PostingThreshold`, 20). MissionService's interception goes through `Add`. The pure `ApplyAdd`/`ApplySet` work on a save table.
- **Wanted list.** Every online player at or over the threshold, highest bounty first (`GetWanted`). Their last known city is the `<key>REGION` part under `Workspace.Regions` (7 cities) that contains their HumanoidRootPart, re-read every `CityRefreshSeconds` (20) and the moment they become wanted; "Unknown" outside every region. `BountyService.FindRegionPart(cityKey)` is the shared region lookup (MissionService uses it for placeholder drop-offs).
- **The board.** A physical board, not a GUI. Bryan's is the Part `Workspace.Qarzin.QuestBuilding.Folder.QuestBoard`: the server finds the first BasePart under Workspace named `Config.Bounty.BoardName` ("QuestBoard", or `BoardAltName` "BountyBoard") that carries a Decal named `FrontDecalName` ("frontface"), and posters go on that Decal's `Face`. If none exists a placeholder board is made (`Workspace.BountyPlaceholders.BountyBoard_PLACEHOLDER`, 16 x 8 studs at Qarzin's region, dropped to the ground with the region box excluded from the ray); posters and placeholder are server-made and swept on start.
- **Posters.** One Part per wanted player in `Workspace.BountyPosters`, named `Poster_<userId>` (attribute `TargetUserId`), in a 4 x 2 grid centred on the face (rows and the block centred, highest bounty first, at most `MaxPosters` 8), `Config.Bounty.Poster` size or 90% of a cell if smaller, flush just outside the face with the board's own orientation. Each carries a ProximityPrompt "Take bounty" (hold 0.4 s, 10 studs) and a SurfaceGui on the same face whose canvas takes the poster's proportions. Reconciled when the wanted list, a bounty or a city changes (`SyncPosters`, `PosterLayout`).
- **Poster portraits (M9-04).** Each poster's SurfaceGui holds a `Portrait` ViewportFrame (a `WorldModel` + `Camera`) above the text; name and bounty sit under it. The WorldModel holds `PortraitClone`, a clone of the wanted player's current character made by `BountyService.BuildPortraitClone` (Archivable switched on for the clone only; Scripts, Sounds, Animators, prompts, Tools, particles, the `Effects` folder stripped; every part anchored and non-colliding; `HumanoidRootPart` as PrimaryPart; posed upright at the origin facing -Z). `PortraitCamera(clone, fov)` frames head and shoulders from the clone's Head and UpperTorso/Torso positions (same "camera in front of the face, looking back" idea as MenuController's preview, with the distance worked out from the head-to-torso span and `Poster.PortraitFov` 30). The clone is rebuilt only when the character is a different model (respawn: the poster listens to the player's `CharacterAdded`), or when an Accessory, Clothing, ShirtGraphic, BodyColors, CharacterMesh, Decal or SpecialMesh is added to or removed from it (debounced `Poster.PortraitSettleSeconds`, 0.75 s); an ordinary poster refresh (name, bounty, city) never touches it, and a character that is mid-knockout (`Knocked`/`Carried` attribute) is retried later so a poster never shows a crumpled body. It is destroyed with the poster. `SyncPosters(set, entries, board, folder, characterOf?)` takes an optional resolver for tests; `GetPortrait(poster)` returns the ViewportFrame.
- **Taking a bounty** (`Take(hunter, userId)`, fired by the prompt). Refused, with the reason sent to the hunter as a `BountyNotice`, when: the hunter is the target; below Adventurer (rank index 3, 600 Magoi); the hunter already holds a bounty; the target is offline, unloaded or no longer wanted; the hunter has no Backpack or the target no character. On success the hunter gets a Tool named `Bounty: <name>` in the Backpack (no handle, can't be dropped, attribute `BountyTarget` = target UserId, tooltip with the bounty), `Progress.Wanted` = the target's UserId, the Player attribute `WantedTarget` = their name, and a `BountyState`. The Tool IS the bounty.
- **Losing the bounty** (`Drop(hunter, reason)`). The Tool is destroyed, `Progress.Wanted` cleared, `WantedTarget` emptied and `BountyState { target = nil, revealed = false, reason }` sent. M9-03 shows `BountyState.reason`, when `target` is nil, as a chat system line. Triggers: the hunter dying (explicit rule: `Humanoid.Died` drops the bounty with `BountyState.reason` "You lost the poster." (no `BountyNotice`), and they must take a poster from the board again; a knockout keeps it); the Tool leaving the hunter's Backpack/Character or being destroyed; the target stops being wanted (cleared, imprisoned, wiped) or leaves; the hunter leaves or starts a new life; `.bounty drop`. A saved `Progress.Wanted` is stale on load and cleared.
- **Tracking.** On take the target's HumanoidRootPart position is snapshotted as `lastKnown`. Every `Tracking.TickSeconds` (1) for each hunter whose Tool is in their Character (checked by the server; `Tool.Equipped`/`Unequipped` and the client's `BountyToolEquipped` only prompt an immediate check): within `ReachStuds` (25) of `lastKnown`, `lastKnown` follows the target; within `RevealStuds` (80) of the target, `revealed = true`; once revealed, staying beyond `RevealStuds` for `LoseSeconds` (6) sets `revealed = false` and `lastKnown` = `lastSeen`, the target's position the last tick the hunter was within `RevealStuds` of them. Nothing is sent while the Tool is unequipped except one final state clearing `revealed` (the last known spot then stays where the hunter last saw the target). Only the tick moves the tracking clock; equip/unequip events never do. The pure rule is `Bounty.NextTrackingState(hunterPos, targetPos?, state) -> state`.
- **Imprisonment seam (for M9-02's JailService).** `BountyService.ClearForImprisonment(prisoner, hunter) -> Reward?`, `Reward = { copper, magoi, gold }`: refused (nil, nothing changes) if the prisoner is not wanted, is the hunter, or either save is missing; otherwise zeroes the prisoner's bounty and pays the hunter once: Copper = the bounty (`EconomyService.GiveCopperValue`), Magoi = 25 + bounty / 4 capped at 50 (`RankService.AddMagoi`), +1 Gold Rukh deed (`RankService.AddDeed`); drops every hunt on the prisoner (the collecting hunter's reason is "Bounty collected.").
- **Attributes (Player):** `Bounty` (number), `WantedTarget` (target's name or "").
- **Save fields:** `Bounty`, `Progress.Wanted` (number?), `Progress.JailUntil` (number, written by M9-02; v5 adds it so one migration covers M9).
- **Remotes (see section 16 for rates).**
  - `BountyState` (server -> client), `{ target = { userId: number, name: string, bounty: number }?, lastKnown = { x: number, y: number, z: number }?, revealed: boolean, reason: string? }`. Sent on take (`target` set, `revealed` false), on drop (`target` nil, `reason` set, no `lastKnown`), on equip/unequip, and each tracking tick only when `lastKnown` or `revealed` changed. The client hides its tracker while `revealed` and red-highlights the target (M9-03).
  - `BountyNotice` (server -> client), `{ text: string }`: a one-line player-facing notice (a refused take, "Bounty collected.", jail replies). The client shows it as a chat system line.
  - `BountyToolEquipped(boolean)` (client -> server): the Tool went into/out of the hands. The server ignores it unless it matches the real state.
  - There are no board remotes: the board is read by looking at it and taken by its prompt.
- **Prisoners.** `JailService.Imprison` drops the prisoner's own hunt.
- **Dev commands:** `.bounty <n> [player]` (set), `.bounty list`, `.bounty take <player>` (full rules apply), `.bounty drop`, `.bounty clear [player]`.

## 18. Carry and jail (M9-02)

Server: `Server/Services/CarryService.luau`, `JailService.luau`. Data: `Shared/Data/Jail.luau` (sentence maths), numbers in `Config.Bounty.Carry` and `Config.Bounty.Jail`. New statuses (StatusService, no duration, each mirrored to a character attribute of the same name): `Carrying` (carrier), `Carried` (target), `Jailed` (prisoner). Movement/Combat tables block run and dash for all three and attack, block-start for all three (a block ends the moment `Carrying`/`Jailed` begins); MissionService refuses `MissionStart` while `Jailed`.

**Carrying (`CarryService`).**
- `CarryPickUp(userId)` (client -> server, 2 per second) and `CarryDrop()`. The server decides: the target must be `Knocked`, within `Carry.ReachStuds` (6) of the carrier, not `Jailed`/`Carrying`/`Carried`, and not the carrier; the carrier must be alive and not `Knocked`/`Stun`/`TrueStun`/`Jailed`/`Carrying`/`Carried`. Refusals are silent for the client (a log line only). The E prompt is client-side (M9-03).
- On pick-up the target's HumanoidRootPart is welded (`WeldConstraint` "CarryWeld") to the carrier's UpperTorso/Torso at `Carry.Offset`, rolled `TiltDegrees` so the body lies across the shoulder; the target's parts stop colliding while carried; the weld joins the carrier's physics assembly, so the carrier owns the body. The target keeps the ragdoll their `Knocked` status built. The carrier walks at `Carry.SpeedMult` (0.6, MovementService modifier `Carrying`).
- Every `Carry.RefreshSeconds` (0.5) each carried target's `Knocked` is refreshed to `Combat.Knockout.getUpSeconds`, so the get-up timer never fires while carried; on a drop they get `Carry.GraceSeconds` (4) of `Knocked`. A dev command that ends their knockout also ends the carry.
- A carry ends when: the carrier drops, is knocked out, dies, respawns or leaves; or the target dies, respawns or leaves. A drop puts the target `Carry.DropDistance` (4) studs in front of the carrier (or at a given spot: the jail uses the cell).
- **`CarryState`** (server -> client, to both parties): `{ carrying = { userId, name }?, carriedBy = { userId, name }?, canDeliver = boolean, dropoffPath = string? }`. The carrier gets `carrying` set; the carried gets `carriedBy`; both nil means a carry ended. `canDeliver` (carrier only) = the carried player is the person the carrier's bounty is on AND a jail exists; it is re-sent when it changes. `dropoffPath` is the full name of the `JailDropoff` part (e.g. `Workspace.Qarzin.QuestBuilding.Jail.JailDropoff`): the client highlights it for that hunter only when `canDeliver`; the server adds no Highlight.
- API: `PickUp`, `Drop(carrier, reason, placeAt?)`, `GetCarried`, `IsCarrying`, `IsCarried`, `RefreshCarried`, `SetDeliveryInfo`.

**Jail (`JailService`).**
- **Bryan's jail:** a Folder `Jail` (names are `Config.Bounty.Jail.JailFolderName`, `DropoffName` "JailDropoff", `CellFolderName` "LargeCell", `SpawnName` "JailSpawn") somewhere under Workspace, today `Workspace.Qarzin.QuestBuilding.Jail`. Found: first descendant named `Jail` with a `JailDropoff` part and a `LargeCell` folder holding a `JailSpawn` part. Cell bounds = the world bounding box of every part under `LargeCell`, grown by `BoundsMargin` (2), re-measured every 10 s. The cell's walls are all named `Jail1`, so nothing is looked up by that name. If none is found, a `hasJail` city (Qarzin) gets a placeholder cell in `Workspace.MissionPlaceholders` (magenta floor, transparent walls, made on first use) with a log line. Qarzin's is the only jail: every city's prisoners go there.
- **`JailDeliver()`** (client -> server, 2 per second). Needs: carrying someone; the hunter within `Jail.ReachStuds` (8) of the `JailDropoff` part's box (not a radius); the carried player is the hunter's bounty (`Progress.Wanted`); that player is wanted. Otherwise refused with a one-line `BountyNotice` ("You are not carrying anyone." / "There is no jail here." / "That is not the person your bounty is on." / "They are not wanted."). On success: `BountyService.ClearForImprisonment` pays the hunter once and zeroes the bounty, the carry ends with the prisoner placed at `JailSpawn`, the prisoner's own hunt is dropped, and they are sentenced.
- **Sentence:** `Jail.SentenceSeconds(bounty)` = `bounty * SecondsPerBountyPoint` (6) clamped to `MinSeconds` 60 .. `MaxSeconds` 600. `Progress.JailUntil = os.time() + sentence`; the Player attribute `JailUntil` (os.time, 0 = free) is published for the countdown, and the character attribute `Jailed` is true while serving.
- **While Jailed:** no run, dash, attack, block or deliveries; `JumpPower` and `JumpHeight` are 0 (the humanoid's own values are restored on release); every `Jail.TickSeconds` (1) a prisoner outside the cell bounds is moved back to `JailSpawn` (the bars have gaps, so this is the real wall). Dying or respawning while serving spawns in the cell (`PlayerService.SetSpawnOverride`), and so does rejoining mid-sentence; the sentence is a timestamp, so leaving never shortens it.
- **Release:** when `JailUntil` passes, `Jailed` is removed, `JailUntil` = 0, jump is restored, the player is moved to `Workspace.MAP.Spawns.QarzinSpawn` (`PlayerService.GetSpawnCFrame`) and gets a `BountyNotice`. A wipe or new life also frees them. No bail, no escape.
- **Dev guard:** `.jail` rejects non-finite or negative seconds and clamps to `MaxSeconds`; `ApplyImprison` clamps the same way (`Jail.SafeSeconds`).
- **Caching:** the Jail folder is found once and kept until it leaves the workspace (a rescan runs at most every 10 s while none exists); only its cell bounds are re-measured when something under it changes. `JailSpawn` may sit inside `LargeCell` or directly under `Jail`.
- **Replaced characters:** a carry remembers the two models it was made with; a drop never moves or touches a character that has since been replaced.
- **Dev commands:** `.jail <seconds> [player]`, `.jail release [player]`, `.carry drop`.

## 19. Gripping (M9-04)

Server: `Server/Services/GripService.luau`; reward path `BountyService.SettleByGrip` / `GripPayout`; numbers in `Config.Bounty.Grip`; statuses `Gripping` (gripper) and `Gripped` (victim), each mirrored to a character attribute of the same name. A hunter kneels over a knocked-out player and chokes them; if nothing interrupts, the victim dies. The gripper can be a Player or an NPC Model (a Target dummy); the grip is a server state, the client only asks.

- **API.** `GripService.Begin(gripper, victim)` (`gripper`: Player or NPC Model; `victim`: Player or UserId; named Begin because `Start` is the service hook) returns `(true)` or `(false, reason)`; `Stop(gripper, reason)` ends it with no kill; `Tick(now?)`; `IsGripping(gripper)`, `GetVictim(gripper)`, `IsGripped(victim)`; pure `Decide(facts)` and `Progress(startedAt, now)`. `GripService.Rewards = { settle, blackDeed }` is what a completed grip pays through (the self-test swaps in recorders).
- **Refused unless** the victim is `Knocked` and not `Carried`/`Jailed`/`Gripped`, within `Grip.ReachStuds` (5) of the gripper, alive; and the gripper is not the victim and not `Knocked`/`Stun`/`TrueStun`/`Jailed`/`Carrying`/`Carried`/`Gripping`/`Gripped`. Refusals are silent for the client (a log line).
- **While gripping.** Gripper: `Gripping` status; walk speed 0 (MovementService modifier `Gripping`, no anchoring); run, dash, attack and block refused through the BLOCKS_* tables in MovementService/CombatService (a block or swing in progress ends the moment `Gripping` turns on). Victim: `Gripped`; their `Knocked` is refreshed to `Combat.Knockout.getUpSeconds` every tick (as CarryService does) so they cannot get up. Character attributes: `GripProgress` (0..1) on the victim, `GrippingTarget` (the victim's name) on the gripper; both are removed when the grip ends.
- **Timing.** A server loop ticks every `Grip.TickSeconds` (0.25): validates, keeps the victim down, publishes progress, and completes at `Grip.Seconds` (4).
- **Interrupts** (all `Stop`, no kill; the victim gets `Grip.GraceSeconds` (2) more of `Knocked` if they are still down and alive): a hit lands on the gripper (`CombatService.HitLanded`, the same signal that interrupts an attack); the gripper becomes `Knocked`/`Stun`/`TrueStun`/`Jailed`/`Carried`; either character dies, is removed, or is replaced by a respawn; either player leaves; the gripper is more than `Grip.BreakDistance` (3) from where they started; the client sends `GripStop`; the victim stops being `Knocked`, or becomes `Carried` or `Jailed`. NOTE for M9-02's owner: CarryService does not yet list `Gripped`/`Gripping` in its blocker tables, so a hunter can pick a gripped victim up and thereby break the grip.
- **Completion.** The grip is torn down first (statuses, modifier, attributes), then: for a **player** gripper, `BountyService.SettleByGrip(victim, gripper)` runs (pays only when the gripper holds the poster on the victim and the victim is wanted: Copper = the bounty, Magoi = 25 + bounty / 4 capped at 50, and the reward's Rukh deed as **Black**, never Gold; zeroes the bounty, drops every hunt on the victim, `BountyNotice` "Bounty collected."; nobody is jailed), and the gripper gets `Grip.BlackRukh` (1) Black deed for every completed grip, bounty or not (these stack on a bounty grip: 1 from the bounty, 1 from the grip). An **NPC** gripper has no player, poster or reward. Then the victim's character gets the attribute `DeathCause` = "gripped by <name>" (LifeService prints it in its death line) and its `Humanoid.Health` is set to 0, so the ordinary death path runs: a life is lost, the last life runs the Rukh scene. **No bounty is ever added to the gripper.**
- **Remotes.** `GripStart(userId)` (client -> server, 2 per second) and `GripStop()` (client -> server, 3 per second). `GripState` (server -> client, to both parties on start, every tick and on stop): `{ gripping = { userId: number, name: string }?, grippedBy = { userId: number, name: string }?, progress: number (0..1), reason: string? }`. The gripper gets `gripping` set, the victim gets `grippedBy` set (an NPC gripper's `userId` is 0); both nil means the grip ended and `reason` says why ("completed", "hit", "moved away", "released", "victim no longer knocked out", ...). Progress is also on the `GripProgress` attribute.
- **Animation.** Bryan makes the real grip animation later; until then the client poses it in code (M9-04-C). `Config.Bounty.Grip.Animations = { Gripper = "", Victim = "" }` takes the asset ids when they exist.
- **Save format:** unchanged.
- **Dev commands:** `.grip <player>` (grip a knocked-out player in reach), `.grip stop`. To test: `.knock` a target, stand within 5 studs, `.grip <name>`; hit yourself out of it with a second account, or walk away; `.bounty 50 <name>` + `.bounty take <name>` first to see the bounty path.
