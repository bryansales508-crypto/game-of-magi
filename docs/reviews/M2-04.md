## Findings

**H1 — high — `MenuController/init.luau:273`.** The cloned `MenuGUI` is parented into `PlayerGui` once in `Start()` and never touched again; the header comment claims it "isn't reset on respawn" because it didn't come from StarterGui. That's backwards: `ScreenGui.ResetOnSpawn` defaults to `true` and applies to *any* ScreenGui under `PlayerGui`, regardless of origin — Roblox destroys it on the character's next respawn and only re-creates it automatically if it originated in StarterGui. This one didn't, so after the player's first death it is silently destroyed and never comes back; the M key then no-ops for the rest of the session (`gui.Enabled` set on a dead instance throws nothing, just does nothing). `HudController`'s own comment (line 7) gets this exact distinction right, and `DevController/init.luau:112` already sets `ResetOnSpawn = false` on its own script-created ScreenGui for this reason. M2-05 (next task, same session) adds the death→respawn cycle, so this will reproduce on the very first playtest death.
**Fix:** set `gui.ResetOnSpawn = false` right after cloning `MENU_TEMPLATE` (`init.luau:273`).

Lower risk in practice (the screen only lives pre-spawn, before any `CharacterAdded`), but it's the same class of bug and cheap insurance — flag for consistency with H1's fix.
