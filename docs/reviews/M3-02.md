## Findings

1. **Critical — `SSS/Interactions/InteractionsHandler.server.luau:10,14` and `SCS/Scripts/PhysicalHandler.client.luau:13,16`.** This commit deletes `Running.model.json` and `CombatRemotes/Dash.model.json`, but both old scripts still do unconditional dot-indexing (`remotes.Running`, `remotes.CombatRemotes.Dash`) at the top of their main chunk, not `:FindFirstChild`. Both instances no longer exist, so both scripts error out immediately on load — killing the server's entire combat/footstep handler and the client's entire input/footstep handler (attack, block, run, dash, footsteps) for every player. SYSTEMS.md §8 discloses this ("they will error until M3-03 deletes them... nothing gets merged or Studio-synced in between"), but that makes it a hard merge gate, not a non-issue: **do not merge/sync this branch to Studio until M3-03 (server) and M3-05 (client, already built) are also on it.** Flagging so the lead enforces that gate explicitly rather than relying on session memory.

2. **High — `SSS/Interactions/InteractionsDesign.server.luau:8-30, 113-238, 278-369`.** Completely untouched by this commit. It still creates its own `IntFold`/`IntFold.MovementSpeed` folder and `SpeedStableWalk`/`SpeedStableRun` values on every `CharacterAdded`, and still writes `character.Humanoid.WalkSpeed` directly in ~20 places. This is exactly the case the task spec itself calls out ("if InteractionsDesign still recomputes WalkSpeed on its own, that's a finding") and it directly undercuts AUDIT M6 (one owner of WalkSpeed) and M3-PLAN's own "Replaces" column, which assigns "the speed and IntFold parts of InteractionsDesign.server.luau" to M3-02. Two systems now race to create same-named `IntFold`/`MovementSpeed` folders (Roblox allows duplicate child names, so which one `FindFirstChild` returns is order-dependent) and both write `WalkSpeed`. Needs at least a targeted no-op/removal of the speed- and IntFold-creation code in `InteractionsDesign.server.luau`, even if the rest of the file waits for M3-03.

3. **Medium — `MovementService.luau:346,349` (introduced by this commit, not pre-existing).** The dash's transient bridge marker is written directly via `writeBridgeModifier(character, entry, "Dash", 1.0)`, which never touches `entry.modifiers`. The cleanup then calls `MovementService.ClearModifier(character, "Dash")` (line 349), which bails immediately because `ClearModifier` (line 246) guards on `entry.modifiers[name] == nil` — true here — and never reaches `clearBridgeModifier`. Net effect: the `Dash` child under `IntFold.MovementSpeed` is created on the first dash and its Value is refreshed on every dash after, but it is **never removed**. `PhysicalHandler.client.luau`'s dash-cancel watches `ChildRemoved` for exactly this child (per this same commit's own SYSTEMS.md write-up) — that cancel path is broken from the second dash onward. Fix: either call `clearBridgeModifier(entry, "Dash")` directly on cleanup instead of going through the public `ClearModifier`, or route the initial write through `SetModifier`/give it a matching `entry.modifiers` entry.

4. **Low — `docs/TASKS.md:105`.** This same commit updates the M3-05/M3-06 rows but leaves M3-02's own row at "queued (same session)" despite finishing it. Update the status/owner column.
