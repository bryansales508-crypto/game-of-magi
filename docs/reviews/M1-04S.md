## Findings

**F1 (medium) Stale "Ready" on respawn: the old AppearanceController and `WaitForReady` can skip the wait.** `PlayerService.luau:139` only resets `JoinState` to `"Loading"` inside its own `CharacterAdded` handler. Roblox doesn't guarantee handler order, so on a respawn `AppearanceController/init.server.luau:70` may run first, still read `"Ready"` from the last life, and start building right away. That skips the loading screen and the new ClientReady. `WaitForReady` (`PlayerService.luau:84`) has the same gap: `IsReady` is still true and `player.Character` is already the new model, so it returns the new character early.
Fix: also call `setState(player, "Respawn")` from `player.CharacterRemoving`, which fires before the next `CharacterAdded`. Also keep a per-player `readyCharacter`, set it in the ClientReady handler and clear it on Respawn/PlayerRemoving, and make `WaitForReady` require `readyCharacter[player] == player.Character`.

**F2 (medium) A character spawned before the listener is connected is missed.** `onPlayerAdded` (`PlayerService.luau:174`) connects `CharacterAdded` but never handles an existing `player.Character`. That happens when `Start()` catches up a player who joined before `Init` ran (Studio Play Solo can do this). The state then stays `"Loading"` forever: only the 120 s warning, and the loading screen never fades. This breaks the "every wait reads the current state first" rule.
Fix: after the Connect, `if player.Character then task.spawn(onCharacterAdded, player, player.Character) end`.

**F3 (low) The spawn raise is a fixed 3 studs from the part's centre** (`PlayerService.luau:119`). If QarzinSpawn is tall or rotated, the character can clip or tilt.
Fix: `CFrame.new(qarzin.Position + Vector3.new(0, qarzin.Size.Y / 2 + 3, 0))`. Or confirm in Studio that the part is thin and flat, and leave it.

**F4 (low) The data wait in `onPlayerAdded` (`PlayerService.luau:178-182`) does nothing:** its result is never used, because `onCharacterAdded` waits for the data itself.
Fix: remove it, or add a comment saying it's a placeholder for M2.

**F5 (low, outside file ownership) The task edited vendored `Packages/ProfileStore.luau`,** which is not one of M1-04S's owned files. The edits are comments only, but the `repeat` line at ~1606 lost its indentation.
Fix: the lead approves after the fact, or reverts and handles it under a setup task.

**F6 (info, pre-existing) `repeat task.wait() until loading == false` (AppearanceController:81) never checks `player.Parent`.** If a player leaves before Ready, that thread spins forever. The old code did the same, and the spec said to change nothing else here. Leave it for M2, but log it against M9.
